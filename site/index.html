Primer

Open addressing keeps every entry in one array#

All three maps store keys and values directly in one array (open addressing) and share one API. A key's hash picks a home slot; on a collision the map probes further slots until it finds the key or an empty slot. The baseline instead allocates a node per entry and chains nodes per bucket. Every measured lookup uses a table fixed at 1,048,576 slots, so the load factor — entries ÷ slots — is the only variable.

LinearMap grows at 70% full, so it has no point at 85%. Robin Hood and SwissMap allow 87.5%.

Lookups

SwissMap has the fastest lookups at every load tested#

The baseline's median rises from 5.0 ns to 16.2 ns across the same loads. Every lookup in it follows a pointer to a separately allocated node, and more entries mean more nodes competing for cache. The open-addressing maps read from one array, and SwissMap usually needs one group of tags plus one key comparison — consistent with its flatter curve, though cache misses were not counted. Even the slowest SwissMap run at 70% beat the fastest std::unordered_map run by 1.44×.[E2]

Tail latency

SwissMap keeps the miss tail lowest#

A miss is the worst case for open addressing: the probe runs until it reaches an empty slot. SwissMap stops at the first group of 8 that holds an empty tag, so long runs of full slots cost it whole groups at a time rather than one slot each. LinearMap has the widest gap between median and p99 (16.9 ns to 27.0 ns), consistent with the long clusters that linear probing forms as the table fills.

Inserts

Sequential keys speed up std::unordered_map, not the open-addressing maps#

The open-addressing maps pass every key through the splitmix64 finalizer, which spreads 1, 2, 3, … across the table as if they were random.[E8] The baseline uses std::hash<uint64_t> as a caller gets it; in libc++, the standard library Apple clang uses here, that hash returns the integer unchanged.

With an identity hash, consecutive keys land in consecutive buckets, so no two keys share a bucket and nodes allocated one after another sit near each other in memory. That is consistent with the sequential speed-up above and with sequential lookups at 70% load taking 63% of the random-key time; the benchmark does not measure bucket occupancy or cache misses directly. The same identity hash would cluster badly in an open-addressing table, which is why these maps mix first.

Correctness

Every map agrees with std::unordered_map on 12 M random operations#

A seeded random program of inserts, overwrites, erases, lookups and clears runs against each map and std::unordered_map side by side; every return value and the size must agree after every step, and a final walk must visit exactly the reference's entries. That is 20 seeds × 200,000 operations for each of 3 key shapes (small range, keys with the low 20 bits zero, full 64-bit), 12,000,000 operations per map.[E6]

Separate tests check Robin Hood's ordering invariant after every operation, that tombstones stay bounded under churn, and growth and reserve behaviour. CI builds with GCC and Clang on Linux and Apple clang on macOS, and repeats the tests under AddressSanitizer and UndefinedBehaviorSanitizer.

Limitations

Results cover one machine, one compiler and synthetic keys#

  • One machine, one compiler. All numbers come from an Apple M5 Pro with Apple clang and libc++; another CPU or standard library can change both the ratio and the sequential-key effect.
  • Shared machine. Load average was 10.51 / 7.05 / 6.70 when the run started, so other processes competed for the CPU. Medians resist that better than single runs; bands show how far it reached.
  • Batch-averaged percentiles. Tail figures describe 64-lookup averages, not single lookups.
  • Fixed key and value types. Keys and values are uint64_t; no strings, iterators or custom allocators.
  • Synthetic keys. Random and sequential keys only; real key sets with structure may hash differently.

Reproduce

Reproduce it in five commands#

Commands run from a clone of allenwang0/hashbench.

  1. Create a local environment with the pinned CMake, Ninja, clang-format and jsonschema.

    scripts/setup.sh && source .venv/bin/activate

  2. Build in Release and run the tests (downloads GoogleTest and Google Benchmark). Expect “100% tests passed”.

    cmake --workflow --preset release

  3. Run the benchmark (10 interleaved repetitions; set HB_REPS to change) and the latency tool, then rebuild this page, the card and the README table from results/.

    scripts/run_bench.sh

  4. Sanitizer build (Debug, ASan + UBSan), tests only.

    cmake --workflow --preset sanitize

  5. Check that the page's numbers match the committed results.

    python3 -m unittest discover -s scripts -p "test_*.py"
